# Build the Bridge First: lead-capture pilot (handoff)

Status: implemented and verified locally (updated after review: confirmed opt-in, privacy policy draft, corrected PDF). **Not deployed, not migrated to production, no real leads emailed.** The only emails sent were to Resend sink addresses (`delivered|bounced|complained+x@resend.dev`) and one to the admin inbox.

See also: [preview-safeguards.md](preview-safeguards.md) · [rollout-checklist.md](rollout-checklist.md) · [content-comparison.md](content-comparison.md) · [convert-next-guide.md](convert-next-guide.md) · [assessment-compatibility.md](assessment-compatibility.md)

## 1. The experience
`/resources/build-the-bridge-first` is a server-rendered page: the complete nine-page guide as semantic HTML (readable without email, login or JavaScript), plus three CTAs: **top** (READ ONLINE / GET THE PRINTABLE GUIDE), **mid-guide** (after the first exercise, page 2) and **end**. Every CTA opens the same inline form (no modal): email only, button "SEND ME THE GUIDE + JOIN THE COMMUNITY →", disclosure beside it, no checkbox. On submit the PDF downloads immediately (served as an attachment from a freshly signed URL) with no confirmation step, the success state shows "DOWNLOAD THE PDF →" as backup, and the delivery email is sent. The email carries a **confirm button**; community marketing starts only after the reader confirms. If the email fails the download still works and the page says so.

Existing resources are untouched: only slugs with an entry in `app/lib/resources/config.ts` use the new page.

## 2. Schema (one additive migration, see rollout checklist)
- `resource_events` new: shared anonymous + identified event stream (any resource type).
- `consent_records` new: append-only (UPDATE blocked by trigger) log: action (`opt_in_requested`, `opt_in`, `opt_out`), exact wording + version, method (incl. `email_confirmation`), `related_record_id` (a confirmation points at the request it confirms), source type/resource/URL, CTA, hashed IP and user agent. Existing opt-in/out timestamps are backfilled as `legacy` rows with unknown fields left NULL.
- `leads` +`lead_status` (new/engaged/qualified/contacted/converted/archived), `last_activity_at`, `suppressed_at`, `suppression_reason`, `consent_requested_at` (a request awaits confirmation).
- `resource_requests` +`resource_action`, `session_id`, `cta_location`, `source_page_url`, `delivery_status`, `delivery_provider_id`, `delivery_error`, `delivery_updated_at`, `download_count`, first/last download.
- Consent *status* (pending / opted_in / opted_out / suppressed) is **derived** in `app/lib/leads/consent.ts`, not stored, so it cannot drift from the live flag.

## 4. Events and formulas
Client may send only: `resource_page_view` (once per session / 30 min), `resource_read_started` (first exercise page scrolled into view), `resource_read_completed` (final page reached ≥ 60 s after start: a proxy, not proof), `resource_cta_clicked`, `resource_form_opened`. Server writes `resource_form_submitted`, `resource_download_started`, `resource_delivery_{queued,sent,delivered,bounced,failed}`. Bots are not counted; Global Privacy Control / Do Not Track send nothing; stored `page_url` is path-only and referrer is hostname-only; no email or IP in events.

Sessions = distinct per-tab session ids on page views. Valid opt-ins = new consent recorded + already-subscribed (excludes suppressed). View→opt-in = valid opt-ins ÷ sessions. CTA→opt-in = valid opt-ins ÷ sessions with a CTA click. Opt-in→download = requests with ≥1 download ÷ requests. All formulas are printed beside the numbers in the admin and unit-tested (`funnel.test.ts`).

## 5. Consent behaviour (confirmed opt-in, wording `resource-guide-consent-v1.1`)
Submitting the form records an `opt_in_requested` row (exact wording, method, source, CTA, hashed IP/UA) and marks the lead **pending**; `ongoing_content_opt_in` stays false, so the address is not in any subscriber export or audience. The guide is delivered immediately regardless. The delivery email includes "Yes, confirm my email →" (signed, 30-day link to `/confirm`, which shows a button; only the POST confirms, so email scanners that open the link cannot). Confirming flips the live flag, stamps the date and appends an `opt_in` row (`email_confirmation`, pointing at the request, copying its wording/source, with the confirming device's hashed evidence) and a `resource_opt_in_confirmed` event.
- Active subscriber: original consent kept, nothing new recorded, email has no confirm button.
- Previously unsubscribed: becomes pending again; reactivated only on confirmation; old `opt_out_at` and history preserved.
- Suppressed (spam complaint): guide delivered, never pending, never reactivated, a forged confirm link is refused; email is a one-off.
- Unsubscribe (neutral `/unsubscribe`, one-click header, legacy Napkin URL) uses one shared function, appends `opt_out`, keeps the guide accessible, and **cancels a pending request** so the old confirm link stops working.
- Status is derived: pending / opted_in / opted_out / suppressed. Admin Leads shows "Awaiting confirmation" as its own filter; the subscribers export contains confirmed subscribers only.

## 6. Email behaviour
Statuses: `accepted` (ours) → `queued` (Resend returned an id) → `sent` → `delivered` | `bounced` | `failed`. Only the signed webhook can set `sent`/`delivered`/`bounced`; without it emails remain "queued". Spam complaint → suppression. Subject "Your guide: Build The Bridge First", stable download link (`/api/resources/download?token=<requestId>&via=email`, signed fresh per click), sender identification, unsubscribe link + RFC 8058 header, idempotency key per request.

## 9. Running it locally
`supabase start` (Docker) → `supabase db reset` → `export LOCAL_ADMIN_PASSWORD='choose-a-throwaway-value'` (any value; only for the local admin user, never commit it) → `node e2e/seed.mjs` (needs local keys from `supabase status -o env`) → start Next with `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` pointing at the local stack and `APP_BASE_URL=http://localhost:3000`. The e2e scripts read the same env (`ui.mjs` and `inbox-test.mjs` also need `LOCAL_ADMIN_PASSWORD`). `supabase init` created `supabase/config.toml`.
